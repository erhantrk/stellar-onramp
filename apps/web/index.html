§ 02

Why the proof is verified only once

A pairing check is expensive and the ledger has a fixed budget, so the proof is checked once and the result is cached.

The cost of a pairing

Verifying a BBS+ proof inside the contract takes about

105 M instructions · once per wallet

Well inside the 400 M a single transaction may use.

The per-ledger ceiling

The 580 M per-ledger cap allows roughly

~8 verifications · network-wide · per 5.5 s

Checking a proof on every transfer would not scale, so the contract verifies once and every later check reads the cached record.

§ 03

Two levers, and both must be pulled

On chain

  • A tombstone — claims set to zero. Never a delete, never a backdated expiry; both are undoable by a holder who kept a held-back attestation.
  • An incremented revocation epoch on the subject, bound into every signed payload.
  • Two doors: one for a human decision, and one so an automated sanctions feed can act in seconds without holding a funded account.

Off chain

  • A W3C Bitstring Status List v1.0 implementation, no network call and no new dependencies.
  • Malformed lists fail closed: 28 malformed inputs, 28 × valid: false, zero throws.
What revocation does not do. The record carries an audit index that ties it to the status-list entry behind it — but the contract never reads it back, and verify-once means the chain never re-verifies. Revoking in the status list does not make a cached on-chain record go false; the on-chain tombstone is what does that.

§ 06

What the contracts guarantee

Each of these runs on the deployed testnet contracts.

Guarantees

  • The proof is verified by the contract, against an issuer key it reads from the registry. No server signature is in the trust path.
  • Only the claims that are needed are revealed. A proof can disclose a subset of the credential's attributes; the rest stay hidden under the same signature.
  • No personal data in the credential. The schema has no field for a name, a date of birth or a document number.
  • A proof is bound to one wallet, one contract, one network and a ledger deadline. It cannot be replayed elsewhere or later.
  • Revocation works on chain and off: a tombstone in the contract and a signed status list from the issuer.

Design decisions

DecisionWhy it was made
over18 is pre-computed, not a range proof BBS+ cannot express a range statement, so the issuer derives the boolean and signs it as an attribute.
subjectBinding is disclosed at the gate The gate already knows the wallet, so revealing the binding there costs nothing; it is not revealed to other parties.
Expiry is a ledger sequence, not a wall clock The contract can only read the ledger sequence, so lifetimes are counted in ledgers and drift slightly against calendar time.
A single admin key Revocation and upgrades are gated by one key. Multi-party control is left to the deployment.
An operator key can only deny, never grant The admin can revoke a record but cannot create one; only a verified proof writes claims.
