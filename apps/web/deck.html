Onramp

KYC once. Prove the claim, not the document. A BBS+ credential verified inside a Soroban contract, cached as a record any contract can read.

The problem

Everyone re-collects the same passport.

Off chain. Every service that must know you are over 18, or not sanctioned, asks for the same documents and keeps a copy. Each copy is a breach waiting to happen, and the answer they actually needed was one bit.

On chain, it inverts. A regulated asset cannot check identity at all without putting identity on the ledger. So either the token stays closed, or personal data goes public.

The solution

Verify once. Prove a boolean. Cache the verdict.

  • A provider verifies the person once. The result becomes a BBS+ credential of twelve booleans, bound to their passkey smart wallet. No name, date of birth or document number in it.
  • The holder derives a selective-disclosure proof revealing only what a given gate asks for.
  • kyc-gate.attest_bbs runs the BLS12-381 pairing in the contract and writes a claim record. No operator signature is in the trust path.
  • Any contract then reads check(subject, OVER_18) for the cost of a storage read — including a SEP-57 verifier that gates a regulated asset.

Why this costs what it costs

The network caps a ledger at 580M instructions, so proving on every transfer would allow roughly eight verifications network-wide per ledger. Verifying once and caching is the only shape that scales — and it is why a relying contract pays almost nothing.

Built on Stellar

  • Soroban contracts, built for wasm32v1-none, deployed on testnet.
  • BLS12-381 host functions — the BBS+ verifier is written straight against them.
  • Passkey smart wallets — OpenZeppelin passkey-kit through the Channels relayer.
  • SEP-57 IdentityVerifier adapter, so a regulated asset can require the verdict.
  • SEP-10/12/38/6 against an anchor: TRY to USDC for a wallet the gate approved.
  • Stellar RPC simulateTransaction from the browser, so a viewer verifies the record without trusting our server.

Three packages published to npm: @stellaronramp/identity, /gateway, /sdk.

How it compares

Most designs ask a contract to trust a key.

ApproachWhat goes on chainWho the contract trustsPersonal data
Attestation registriesA record an issuer wroteThe issuer's accountWhatever the issuer puts in it
SEP-57 reference verifierStored claim signatures, country per walletA registry of claim issuersClaim data on chain
Groth16 / UltraHonk proofsPublic inputs after an in-contract checkA verification key per circuitOff chain, but a circuit per claim
OnrampA record written only after an in-contract BBS+ checkThe issuer's public key and the pairing itselfNone, anywhere

BBS+ gives selective disclosure from one signature: no per-claim circuit, no trusted setup. Among Stellar identity projects we surveyed, nobody else uses it.

Honest state

Real

  • Three contracts deployed on testnet; every wasm fetched back and compared byte for byte.
  • A passkey wallet deployed per account, ownership verified on chain.
  • Credential, proof, in-contract verification, cached record, browser-side reads.
  • Anchor flow through quote and deposit instructions.
  • 920 TypeScript tests, 53 Rust tests.

Not real yet

  • The KYC provider is mocked — it verifies what the wizard typed.
  • The demo's passkey is a server-side software key, discarded after deployment.
  • Testnet only; the issuer seed is public by design.

Next

A real provider, a real passkey, mainnet.

  • Swap the mock for a KYC vendor behind the existing provider seam. The credential and contract paths do not change.
  • Move the authenticator into the browser so the passkey is the person's own.
  • Revocation in the portal — the contract and the status list already support it.
  • Mainnet behind a multi-party admin key.
